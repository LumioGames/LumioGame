# Bomber 101 configuration source

`tables/*.txt` and `schemas/*.json` are the authoring source. Row identities are in `registry/row-ids.json`; retired Sample identities remain in `registry/tombstones.json`. IDs and enum codes identify content; they are not balancing values. Never reuse a retired ID. There are 27 tables and 155 rows covering match/life/movement, reinforcement, terrain/material rules, drops, regeneration/final circle/chests, object budgets, characters/skills/effects, Bot difficulty/tactics and presentation.

The immutable API is `BomberConfigBinding.For(world) : IBomberConfig`. Singleton rows are available as `Game`, `Map`, `Movement`, `Bomb`, `Life`, `Drops`, `Regeneration`, `FinalCircle`, `Chest`, `ObjectBudgetRules`, `SkillRules`, `BotTactics`, `Presentation`; `ObjectBudgets` contains the validated effective capacities and requirements. All generated tables are under `Tables`. Use `Attribute(name)`, `SpeedTier(tier)` and `SkillLevel(skillId, level)` for keyed reads. The only attribute seeds are HealthPoints, BombPower, BombCapacity, AvailableBombs, SpeedTier and MovementSpeedMilli. `HatCount(basePower, baseCapacity, baseSpeedTier)` reads reinforcement base ledgers; inventory or temporary speed modifiers never enter it.

## Generation

The synchronization tools use the selected complete Engine release's official `tools/config-compiler.mjs` when it bundles `tools/authoring.mjs`. Set `LUMIO_CONFIG_ROOT` or `LUMIO_ENGINE_CANDIDATE_ROOT` to that complete release directory when verifying a candidate. The supported source-authoring route uses Python 3.11+ and the official `LumioConfig/tools/lumio_config.py` CLI. This authoring dependency never adds a Runtime project reference to the game.

From the game root:

```text
node Tools/sync-config-readers.mjs
node Tools/sync-config-export.mjs
node Tools/sync-config-readers.mjs --check
node Tools/sync-config-export.mjs --check
node --test Tools/bomber-config.test.mjs Tools/sync-config-readers.test.mjs Tools/config-side-isolation.test.mjs
```

The CLI exports into fresh temporary roots with `export --root ... --client-out ... --server-out ... --csharp-out ...`. The export tool runs every configuration twice and requires identical bytes, including manifests. Readers under each end's `Config/Generated` are exactly the compiler's output. The M9 constructor adapter `Gameplay/Config/BomberTypedTables.cs` is generated by the Reader synchronization script from those same schemas and strictly parses the loader's validated snapshot cells. Missing or malformed cells fail; there are no fallback tuning numbers.

Both end projections contain public gameplay rules (`CS`). This game currently has no secret server-only balance field. Movement, bombs, base attributes, speed tiers, life and block behavior explicitly mark shared prediction columns. Server packages still use the official S+V split layout, with an empty V target when no native-only table is declared. Public Bot settings are needed in the C# client Bot. A Reader from one end is never compiled into the other end's assembly.

## Units and provenance

Column names carry units: `_ms` means integral milliseconds; `_ticks` and tick windows are logical engine ticks; `_permille` uses 1000 as unity; `_cells` and map dimensions are grid cells. Movement speeds use milli-cells/second; assist distances, pickup distance, footprint and forward reach use milli-cells. Damage, healing and HealthPoints use half-heart points. Attribute `initial/minimum/maximum/upgrade_step` use their named attribute's unit: half-heart points, bomb/power counts, upgrade tiers or milli-cells/second. All remaining numeric fields are counts, weights, stable IDs or enum codes.

Every source row carries `source_status` and `source_ref`. `design` refers to the product rules/ADRs; `prototype-candidate` values are the selected first-round candidates awaiting playtesting. The old 19/8 geometry used pickup radius 500 milli-cells and pond span at most 3 cells; spawn search enumerates legal cells once. Pond span is a legacy fixture, not a restriction on the current moat design. Object budgeting uses effective producer and lifetime bounds after all profile overlays. Its old 19/8 source is design section 7.6 and ADR-0046. The reservation and retirement allowance of two ticks is a first-round inference; production residence still needs proof. New 12/23 and 16/27 producers require fresh capacities. Periodic/duration Effect SDK semantics, related skill timing, and Effect request/result matching remain pending. Authored numeric durations remain inputs, including fireDash `wall_ms` for capacity arithmetic; this does not approve runtime Effect semantics. Regression seeds 101/202/303/404/505 are fixed test identities chosen for this round. Game block kinds 0–10 map to official catalog identities: air 0 and Bomber entries 1022–1031. Historical catalog IDs remain allocated. Packed BlockId values use the engine conversion API.

The skill balance rows marked `prototype-candidate` migrate numeric values from fixed Game commit `af385a9cd0f261317e97240a7e55accdda8d01d5`. Their references name the original prototype contract file and its ADR 0034 or 0044; ADR 0034 is the published character balance decision, while the unpublished workspace ADR moved to 0045. This numeric migration does not complete structural M1/M2 reconciliation or production Effect behavior.

`ObjectBudgets` uses effective SDK ticks after all overlays. Let `P=8`, `A=width*depth`, `Q=placements per participant tick`, `S=reservation/retirement slack`, `F/D=SDK ticks of fuse/danger`, `M/C/L/R=SDK ticks of match/circle/regen stop lead/regen interval`, and `T=SDK ticks of the first regeneration trigger`. The exclusive stop is `stop=max(0,M-(C+L))`; whole opportunities are `E=T<stop ? 1+(stop-1-T)/R : 0`. With `O=max_mirror_orbits`, regeneration cells are `E*4*O`, and `H=spawn_chest stage count * issuances per stage` is the separate strong-chest count. Required pickups are `A*initial_mint_generations*initialSoftMaximum + E*4*O*resourceMaximum + H*strongMaximum + completeSupplyOutputs`. Each reward maximum includes every possible output whose probability is nonzero; probabilities never discount capacity. Global `ChestLimit=E*4*O+H` describes lifetime issuance, while `PerBombContactLimit` reads the actual generated ContactedChests capacity and has a separate traversal proof obligation.

Required bombs are `P*(max(attributeBombCapacity,Q*F)+Q*(D+enabledFireBurnTicks+S))+128+admittedFrenzyPlacements`; the actual linked Fire level's authored Native Burn residence is charged while Fire is enabled. Required existing wall zones remain `P*wall_casts_per_participant_tick*(W+S)`, where `W` is the largest supported authored wall duration in SDK ticks. Favorite fire regions require an additional producer proof before their budget is admitted. All arithmetic is checked. Default required pickups are1351 with skills and1106 without; the author provision1607 covers the42 named Legacy profiles. A480-second/90-second composite requires1703 with skills and an explicit matching override;1607 is not a UGC ceiling. Unsupported M2/Split production remains rejected, and formula admission does not establish every runtime queue, shared producer or full-world storage bound.

Millisecond-to-tick conversion in gameplay must use SDK `Ticks.FromMilliseconds`. At 20 Hz, buffer 125 and 100 ms both truncate to 2 ticks; 150 ms is 3 ticks. The authoring compiler's optional `seconds` conversion has different rounding, so these sources deliberately keep milliseconds and do not ask it to convert seconds.

## Profiles and derived cells

`profiles.json` enumerates48 profiles:16 core balance variants,24 additional design variants, the product profiles `skills-on`/`skills-off`, and six M2 authoring/room profiles whose runtime admission remains closed. The default enables skills; `skills-on` deliberately repeats that selection. Each profile declares its independent parameter and all derived cells. Overlays live only in LumioConfig's recognized `layers/product/` layer; unknown layer names fail the sync tool. Stable rows and schemas never change per profile.

Derived cells preserve these invariants:

- Power/health initial changes also move the corresponding lower/upper bound.
- A base-speed change regenerates every speed tier as `min(base + tier * step, cap)`, while retaining nine ledger tiers. It also changes the minimum base speed.
- Final-circle duration keeps the first preview/effective stage at 10000 ms. Later offsets are proportionally scaled within the remainder of the circle duration, then truncated to a 20 Hz tick boundary. Every stage remains before the new deadline; no 110-second stage survives in the 90-second variant.
- Late poison, death skill drop rate and bomb-skill candy weights update their dependent stage/skill rows together.

Select server `Server/Config/Profiles/<name>` and client `Client/Config/Tables/profiles/<name>` together. For the default use `Server/Config/Tables` and `Client/Config/Tables`. The client packaging includes all profile roots for local comparison; each profile root has its own manifest and C-only projection. Readers remain shared because the schema is identical.

## 4. Own-bomb collision prevents a claim of full solver parity

`MoveAbility.Server.cs:CanLeaveOwnBomb` requires un-kicked Fuse bomb, full participant match, full `SourceLife == playerId`, exact SourceLifeGeneration, current participant CurrentLife and exact player/participant generation. Bomb SourceLife and SourceLifeGeneration are formally Scope.None. Even after memory and participant generation are visible, blindly sharing this guard conservatively prevents the client from predicting exit from a server-projected bomb under its feet.

Bomb Owner alone names a participant and cannot distinguish a previous life or generation. Do not replace the guard with Owner equality, expose the private fields as an unreviewed convenience, or copy input/history into a second bomb/life table. The existing Room-visible `BomberPresentationJournal` does contain complete life/gen/bomb IDs in `bomb_placed`; however its occurrence is explicitly display-only, bounded to 128 entries and retained for 200 ticks. It is not a collision capability and cannot become durable gameplay state or authorize a late baseline's own bomb.

Therefore the smallest safe first solver proof is ordinary unblocked movement with no such private collision dependency. Keep full server checks and conservative client behavior until an independently reviewed formal logical collision-permission seam exists. An actual own-bomb exit, previous-life bomb and kicked bomb test must remain an explicit unresolved qualification. This limitation means that ordinary predicted movement success cannot be called complete smooth bomber movement.

## 5. Complete result to original Model: real APIs and unresolved display detail

Current Game PlayerEntity has LogicTransform and no ModelTransform. `SpectatorReplicaHost` installs NullPresentationSink, returns the confirmed replica World and sends `PresentationDump` poses taken from its LogicTransform. JS adapter/feed interpolate confirmed snapshots; neither PushSample nor UpdatePresentation is called. Thus a successfully moved prediction target would presently remain invisible.

Existing Runtime public APIs are `PredictionPublished`, gated `PredictedWorld`, immutable `LastPresentationKeyDelta`, `ModelTransform.PushSample(TransformSample)` and `UpdatePresentation(double)`. TransformSample contains exact entity, source Tick, visual TimeSeconds, complete Pose, reference, Teleport and Parent. Model is pure display state; it never writes Logic or enters the persisted logical state. Runtime's normal publication sets the new delta only after Native complete succeeds; its DiffPresentationKeys creates three new list objects each publication, including empty lists. ClientSession already compares these three list references to recognize a new complete publication; Tick and enqueue-return alone do not identify one.

Candidate minimal Game Host seam: at the idle owner boundary, recognize the newly published immutable collection identities; validate current bound Self/life/generation; immediately copy the complete *published* owned Logic pose value; push one immutable sample into the same original confirmed client entity's Model. Do not keep a mutable World/Logic component across boundaries, export candidate World dumps or write prediction pose into confirmed Logic. Remote entities continue using completed authority poses. On generation/life/AOI recreation, use the new original component and discard old visual publication bookkeeping. Existing Native DataWait or closed publication produces no new sample. This is derived presentation bookkeeping, not a new gameplay state owner.

The existing generator rejects an EntityType declared in both shared `PlayerEntity.cs` and a `.Client.cs` fragment. HasAttribute has no Side parameter. Do not assume a new client partial attribute, or a textual #if around Has, yields client-only Model qualification. A shared Has(ModelTransform) declaration may be a narrow candidate with Server Model inactive and only original client Model sampled; this changes the declared component bag and requires actual generator/clone/persistence review. Existing clone code rents the same component bag but copies only generated Sync/Persist fields; the Model in a prediction clone must never become a second active display Model. A generator feature/ADR change is a separate owning Runtime scope if genuinely needed, not part of this narrow solver fix.

Model currently accepts up to 32 complete samples, same-Tick different visual time, ignores exact duplicate sample times/stale samples and jumps on a new explicit Teleport. It has interpolation and bounded 0.1s extrapolation but no dedicated corrective-error convergence API. Calling its current methods does not prove ordinary errors converge smoothly. Visual time is Host monotonic time only; it never determines movement step or world Tick. Current JS feed adds fixed-Tick interpolation and handles same-Tick replacement, so owner Model consumption must also be tested for double delay and duplicate correction/teleport events rather than stack smoothing blindly.

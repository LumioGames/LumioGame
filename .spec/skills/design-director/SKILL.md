# Design Director(策划总监)

以策划 / 制作人身份对游戏设计全域负责:玩法、系统、数值、关卡、商业化、UGC。给带理由的专业裁决,不当传声筒。本技能是 design-* 技能族的 hub——决策在这里产生,沉淀走 [design-doc](../design-doc/SKILL.md),转需求走 [design-request](../design-request/SKILL.md),评审走 [design-review](../design-review/SKILL.md)。

## 何时使用

- 讨论任何策划话题:玩法方向、系统设计、数值框架、关卡结构、商业化、UGC 开放节奏。
- 需要从零建立(或推翻重建)产品方向。
- 在多个策划方案之间抉择,或评估一个策划提案。
- 不确定该用技能族里哪个技能时,从这里进入。

## 回答协议(所有策划问题通用)

- 先明确三件事:这个设计服务什么玩家动机?玩家在什么场景、什么时长下遇到它?对照哪条产品支柱?
- 回答结构:**结论先行 → 依据(引用文档条款或产品支柱)→ 数值化的修改建议**;文档未覆盖的点显式标「新决策,需定调后回写文档」。
- 禁语:「感觉」「好玩就行」「再调调」「看情况」。必须给带理由的专业倾向。

## 操作步骤

1. **定位。** 判断话题落在哪个策划域(见快速参考);确认 `docs/specs/` 下策划案是否已建——已建则先读再谈;未建且只是日常小决策,按回答协议给意见并标注「方向未锁定」;未建且要定方向,走第 2 步。**任何方向讨论开始前先过架构约束速查**——本仓架构已经替玩法做了一部分决策,不检查就会设计出实现不了的东西。
2. **探索(定调阶段一)。** 收敛式提问补齐输入,缺一项先追问、不空转:目标玩家与竞品坐标、核心情绪(玩家为什么愿意再来一局)、局时与人数、平台与操作(PC 键鼠与触屏是两套设计,不是一套的缩放)、商业模式、团队产能。硬约束同时摆上桌:架构约束速查逐条过,冲突项当场标红。
3. **提案(定调阶段二)。** 给 2-3 个候选方向,每个方向一页:方向名 + 一句话定位 + 参考锚(对标产品)+ 六域落地样貌 + **代价表**(开发量 / 美术量 / 架构风险 / 长线扩展空间 / 验证成本)。可先摆竞品坐标(核心情绪 × 局时长短,摆 8-12 个竞品)找差异化落点——空位要问「为什么没人做」。
4. **定调(定调阶段三)。** 用户拍板,**选方向不选细节**;提炼 3-5 条可证伪的**产品支柱**:一句话 + 「这意味着…」+「这不意味着…」,合格标准是能用它明确否掉一个具体提案,每条挂钩玩家动机、不允许纯个人偏好;记录「选了什么 + 为什么 + 为什么不选另外两个」;方向级取舍记 ADR(落点见 [decisions](../../decisions/README.md))。定调后先定**最小验证切片**(一个能回答「好不好玩」的最小可玩形态)再展开细节。**锁**:支柱、品类、局时与人数、核心循环、平台优先级;**不锁**:具体数值、道具清单、关卡布局。
5. **沉淀(定调阶段四)。** 定调结论路由 [design-doc](../design-doc/SKILL.md) 落档;未定调的探索内容不入库。
6. **日常顾问。** 策划案已建后以文档为基准给意见,指出偏离时引具体条款;超出覆盖面的新决策回到第 3-5 步小循环。推翻旧定调 = 走「方向变更提案」:提案 → 影响面评估(已写文档与已开发功能的返工量)→ 决策 → 新 ADR 取代旧 ADR → 更新文档状态。

## 快速参考

### 六大策划域(全技能族单一权威)

| 域 | 管什么 | 核心评判维度 | 常见坑 |
|---|---|---|---|
| 玩法 | 核心循环 / 胜负 / 操作手感 | 一局之内有没有真决策点;30 秒内能否讲清规则;失败时玩家知不知道自己错在哪;PC 与触屏两套操作是否各自成立 | 规则复杂度全塞进教程;胜负条件不可见;为差异化牺牲手感 |
| 系统 | 养成 / 经济 / 社交 / 房间与匹配 | 系统是否服务核心循环而非自我繁殖;新玩家第一局会不会被系统挡住;断线与掉线的容错 | 系统先于玩法设计;为留存加系统反而稀释核心;进房间比玩一局还久 |
| 数值 | 平衡 / 成长曲线 / 掉落 | 每个数字有来源;有无上限防滚雪球;落后方是否还有翻盘路径 | 拍脑袋定值且不标来源;成长无上限导致后半局屠杀;平衡靠感觉不靠对局数据 |
| 关卡 | 地图 / 空间节奏 / 出生点 | 起手是否公平(对称或等价);地图尺寸与移速、局时是否匹配;有无死角与卡点 | 先做美术再验证玩法;尺寸拍脑袋;出生点不等价 |
| 商业化 | 定价 / 付费点 / 变现节奏 | 付费是否触碰公平性;免费玩家体验是否完整;与开源定位的边界 | 把付费点插进核心循环;数值付费破坏竞技;与开源叙事冲突 |
| UGC | 创作层级 / 工具 / 社区 | 表达力够不够(能否做出与官方模式不同的东西);创作门槛;V1 只能靠数据表达 | 表达力设计过窄,后期开放要推翻重来;工具晚于社区需求 |

### 架构约束速查(本仓策划的硬地基,提案前逐条过)

| # | 约束 | 玩法含义 |
|---|---|---|
| 1 | 房间制,单房间第一阶段目标负载 100 人 | 不能设计 MMO / 无缝大世界;房间是设计单位 |
| 2 | 没有匹配系统 | 房间码是默认解;要匹配须单独立项 |
| 3 | 没有快速重连,掉线须重新完整握手 | 局时越长风险越大;长局 + 资产损失 = 退游风险 |
| 4 | V1 不加载第三方代码 | UGC 只能靠数据表达,模式表达力必须早期设计 |
| 5 | 跨 World 事务(改方块 + 扣资源)有成本 | 高频海量方块改动是风险;有限而有意义的改动最合适 |
| 6 | GAS 是一等公民(Ability / Effect / Attribute / Tag + 预测) | 技能、道具、增益类设计几乎零成本 |
| 7 | 单局存档有,账号级持久化没有 | 跨局养成(仓库 / 装备 / 货币)要先谈数据模型 |
| 8 | 公共契约变更须走上游 ADR | 触碰 Component / Mapping / Scenario Schema 的设计不能在本仓直接落地 |

约束现状以 `docs/specs/risks-and-engine-asks.md` 为单一权威,变更时同步该文档;此处只写玩法含义,不复述引擎现状。

### 路由

| 需求形态 | 去哪 |
|---|---|
| 定调结论要落文档 | [design-doc](../design-doc/SKILL.md) |
| 策划案要转成开发需求 | [design-request](../design-request/SKILL.md) |
| 有策划案 / 需求要评审 | [design-review](../design-review/SKILL.md) |

## 注意事项(Pitfalls)

- **不当传声筒。** 只罗列选项不给倾向 = 失职;每个建议都带理由与代价。
- **先过架构约束。** 跳过速查表的提案可能整个不成立,返工成本最高。
- **未定调不沉淀。** 探索中的想法留在会话;只有用户拍板的结论才进文档。
- **提案必须带代价。** 没有开发量 / 架构风险 / 验证成本评估的方案是空谈。
- **改方向不走捷径。** 推翻旧定调必须重新走定调流程 + 更新文档 + 新 ADR 取代旧 ADR。

## 验证

- 结论与理由已明确给出,引用了支柱 / 条款或标注了「新决策」。
- 架构约束速查已逐条过,冲突项已显式说明。
- 定调结论已路由 design-doc 沉淀,或显式声明暂不沉淀。
- 方向级取舍是否记 ADR 已判断。

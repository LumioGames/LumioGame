# Design Review(策划评审)

对照策划案与架构约束审查策划文档与开发需求,产出三级裁决与可执行修改意见。文档基准在 `docs/specs/`(落点定义见 [design-doc](../design-doc/SKILL.md))——审查只对照、不立法。

## 何时使用

- 收到策划案、玩法方案、需求单需要评审。
- 策划案定稿前的质检;检查设计是否偏离既定方向。

## 操作步骤

1. **定基准(含降级)。** 读对应策划案与 [design-director](../design-director/SKILL.md) 的架构约束速查。**策划案未建立时**:显式声明「无策划案在案,按架构约束 + 会话内临时基准评审,结论不具约束力」;评审后把暴露出的空白路由 design-director 定调——**绝不静默发明规范**。
2. **四层对照,前层不过后层不看。**
   - **L1 架构可行性**:逐条过架构约束速查。**这一层不过,后面全部不用看**——设计再好,做不出来等于零。机器可判的约束(局时、人数、是否需要匹配 / 重连 / 跨局存档)先过。
   - **L2 方向符合性**:产品支柱逐条对照;与已定稿策划案的上下游是否一致;是否偏离既有定调。
   - **L3 数值来源完整性**:每个数值是否带「已验证 / 推断待验证 / 引用」标注;推断值是否都进了「待验证项」并写清验证方式。
   - **L4 验收可判定性**:文档的验收问题能否回答是 / 否;需求单的验收标准能否客观验证。
3. **裁决(三级)。** 通过 / 有条件通过(条件清单 + 截止时间,登记为债务、不阻塞下游)/ 退回。退回意见每条:问题定位(文档路径 + 章节)+ 违反条款(降级模式注明临时基准)+ **数值化期望**(「局时上限写成 3 分钟」,不写「局时短一点」)+ 严重级;单次退回聚焦 ≤3 个主要问题,小毛病并入条件清单。
4. **回流。** 同类问题第二次出现 → 记 [lessons](../../knowledge/lessons.md);同类退回 3 次 → 路由 design-director 定调后由 [design-doc](../design-doc/SKILL.md) 补条款,需求单格式问题另修 [design-request](../design-request/SKILL.md) 模板。

## 快速参考(域 × 差异化检查点)

| 域 | 检查点 |
|---|---|
| 玩法 | 30 秒能否讲清规则;失败时玩家知不知道自己错在哪;PC 与触屏两套操作是否各自成立 |
| 系统 | 是否服务核心循环;新玩家第一局会不会被系统挡住;断线容错是否与局时匹配 |
| 数值 | 有无上限防滚雪球;落后方翻盘路径;每个数字来源齐全 |
| 关卡 | 起手是否公平;地图尺寸与移速、局时是否匹配;出生安全区是否足够 |
| 商业化 | 付费是否触碰公平性;与开源定位是否冲突 |
| UGC | 表达力够不够(能否做出与官方不同的模式);V1 数据表达的边界 |

通用评判维度见 [design-director](../design-director/SKILL.md) 六域表,此处不复述。

## 注意事项(Pitfalls)

- **架构可行性优先。** L1 不过 = 整体不通过,不必再评玩法好坏。
- **无文档不硬审。** 降级必须显式声明,结论不具约束力。
- **裁决要引条款。** 「感觉不好玩」不是审查意见。
- **审查不顺手立法。** 空白走定调流程,不在审查里现编规范。
- **数值无来源 = 未完成。** 不因「看起来合理」放行。

## 验证

- 基准来源已声明(策划案章节 / 临时基准)。
- 四层逐层过,L1 结论明确。
- 三级裁决明确;每条意见含定位、依据、数值化期望、严重级。
- 规范空白与复发问题已回流,或声明无。

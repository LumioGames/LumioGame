# 0018 · 解决 v1.1.0 登记的两条契约缺口:DamageApplied 补来源炸弹身份、两个区间默认值收敛为单值

- 日期:2026-09-04
- 状态:生效

## 背景

契约 v1.1.0(`stage0-kernel-contract.md` §7)登记了两条已知缺口,当时都判为「须单独决策后落地」,因而未在该版解决:

- **K1**:`DamageApplied` 只带 `SourceBombOwnerNetEntityIdRaw`(主人)与 `ChainId`,**不带来源炸弹本身的身份**。这与两条已锁的设计要求直接冲突——`design.md` §7.5 规定「同一颗炸弹对同一玩家最多命中一次」,§9.6 规定「死亡回顾列出每个伤害来源的**炸弹**、主人与 ChainId」。规则本身服务端可用按 bombId 的临时命中记忆强制执行,但**事件流无法逐炸弹归因**:同一主人在同一 Tick 放的两颗弹,在遥测与死亡回顾里分不开。用例矩阵 2.4 因此被降级为只验主人与 ChainId。
- **K2**:`dangerWindowMs` 默认值写作 `350–400`、`inputBufferMs` 写作 `100–150`,是**区间不是整数**,与 §5 表头「全部整数」及 config IntegerOnly 纪律冲突,执行者无法把 `350–400` 写进整数配表。另有一处不自洽:`dangerWindowMs` 的出处列声明了 A/B `300/500`,但 §5 的变体清单里没有对应的变体文件。

两条都卡在 G-5(Config 表)开工前面,不解决则实现卡无法落地。

## 决策

- **K1 解决:`DamageApplied` 增加 `SourceBombNetEntityIdRaw:u64`。** 这不是新增产品语义,而是让契约满足 `design.md` §7.5 与 §9.6 **已经锁定**的要求——原契约缺这个字段属遗漏而非有意取舍。字段沿用本仓既有的 `*Raw` 裸 u64 编码纪律(`NetEntityId` 不满足 `Sync<T>` 隐式约束)。用例矩阵 2.4 恢复「字段含来源炸弹」的完整断言。
- **K2 解决:两个区间收敛为单值,并补齐缺失的 A/B 变体。**
  - `dangerWindowMs` = **400**(取 `design.md` §7.1 A/B 三档 `0.3 / 0.4 / 0.5` 的中档,使默认值落在 A/B 序列上、两侧对称可测),补变体 `danger-300` 与 `danger-500`。
  - `inputBufferMs` = **125**(取原区间 `100–150` 中点),补变体 `buffer-100` 与 `buffer-150`。
  - 两个值**仍标「推断待验证」**,按 `design.md` §15 数值来源纪律进待验证表;本 ADR 只解决「不可表达」,不宣称数值正确。
  - A/B 变体总数由 14 增至 **18**;「每个变体只改一键」的纪律不变。
- **锁与不锁**:锁「`DamageApplied` 带来源炸弹身份」「两个键必须是单一整数」「变体清单与 §5 表一一对应」。不锁具体数值(400 / 125 全部可经 A/B 调整)。

## 后果

- 契约升 **v1.2.0**:§3 事件表、§5 Config 表与变体清单、§7 缺口表(K1 / K2 标记已解决并注明由本 ADR 落地)随之修订;`Bomber/Contracts/Events/BomberEvents.cs` 改动使冻结物 sha256 重算。
- `stage0-test-matrix.md` 2.4 恢复完整断言;`design.md` §7.1 / §6.1 / §7.5 / §15 的数值与「受限」说明同步;G-1 / G-5 卡按新字段与 18 个变体改写。
- K1 补字段使 `DamageApplied` 的网络包络多一个 u64,C-1 在架构源登记时须包含该字段;这是本仓玩法层内部 DTO 的形状变化,不改写任何公共语义。
- 代价:`dangerWindowMs` = 400 落在 A/B 序列中档,意味着默认值与 `danger-400` 等价,变体文件因此只需 300 / 500 两个而非三个;若后续把默认值移出 A/B 序列,须同时补第三个变体。
- 代价:两个数值由本 ADR 直接定而非经真人测试,风险由「仍标推断待验证 + 进 §15 + 有 A/B 变体可回退」承担。
